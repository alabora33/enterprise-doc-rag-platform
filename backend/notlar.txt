    Bağlantı havuzu oluşturur. pool_pre_ping ölü bağlantıları

    FastAPI Depends() ile kullanılır. yield ile session endpoint'e
    verilir, istek bitince (hata olsa bile) finally ile kapatılır.

SQLALCHEMY NEDEN KULLANILDI?
========================================================

TEMEL AVANTAJLAR
- ORM: Tablolar Python sınıfı, satırlar Python nesnesi olur
- SQL Injection koruması: Parametreler otomatik escape edilir
- DB bağımsızlığı: PostgreSQL/MySQL/SQLite aynı kodla çalışır
- Relationship yönetimi: JOIN yazmak yerine user.documents gibi

- psycopg2   : Çok düşük seviye, her şey elle

========================================================
SESSIONLOCAL — autocommit=False ve autoflush=False
========================================================

## autocommit=False — Neden?

Veritabanında her işlem bir "transaction" içinde gerçekleşir.
autocommit=True olsaydı her SQL cümlesi anında DB'ye yazılırdı,
geri alınamaz ve hata yönetimi imkansız olurdu.

autocommit=False ile:
  - Değişiklikler db.commit() çağrılana kadar DB'ye yazılmaz
  - Hata olursa db.rollback() ile her şey geri alınır
  - Birden fazla işlem atomik yapılabilir (ya hepsi ya hiçbiri)

Örnek senaryo — doküman yükleme:
  1. Dosya kaydı DB'ye eklendi
  2. Celery kuyruğuna görev eklendi
  3. Kullanım sayacı güncellendi
  → 2. adımda hata olursa commit yapılmaz,
    yarım kayıt DB'de kalmaz, rollback ile temizlenir.

## autoflush=False — Neden?

flush = session belleğindeki değişiklikleri SQL'e çevirmek
        (ama henüz commit etmemek)

autoflush=True olsaydı her db.query() çağrısından önce
SQLAlchemy otomatik flush yapardı. Bu:
  - Beklenmedik DB yazımlarına yol açar
  - Henüz hazır olmayan veriyi DB'ye gönderebilir
  - Özellikle Celery worker'lar ve karmaşık işlemlerde
    sıra dışı davranışlara neden olur

autoflush=False ile:
  - Flush kontrolü tamamen geliştiricinin elinde
  - İstersen db.flush() ile erken flush yapabilirsin
  - Performans: gereksiz SQL round-trip olmaz

## ÖZET

  autocommit=False + autoflush=False = maksimum kontrol
  Kurumsal projede veri tutarlılığı performanstan önce gelir.
  RAG pipeline'da doküman → chunk → embedding → vector DB
  zinciri gibi çok adımlı işlemlerde bu kontrol hayati.

__tablename__ = "users"

ALEMBİC — VERİTABANI MİGRATION YÖNETİMİ
========================================================

## NEDİR?
SQLAlchemy modellerini okuyarak veritabanı şema değişikliklerini
otomatik üreten, versiyonlayan ve uygulayan araç.
Django'daki makemigrations/migrate ikilisinin SQLAlchemy karşılığı.

## NEDEN KULLANDIK?
Ham SQL ile şema yönetmek kaosa yol açar:
  - Hangi sunucuda hangi ALTER TABLE çalıştırıldı?
  - Takım arkadaşı bu değişikliği aldı mı?
  - Hata olursa geri alınabilir mi?
Alembic tüm bunları çözer.

AVANTAJLAR
- Migration dosyaları Git'e eklenir → takım senkron kalır
- Her migration versiyonlanır → DB'nin hangi versiyonda
  olduğu alembic_version tablosunda tutulur
- --autogenerate: model değişince SQL'i sen yazmıyorsun
- upgrade/downgrade: ileri ve geri alınabilir
- Üretime güvenle deploy edilebilir

========================================================
YAPILAN YAPILANDIRMALAR VE NEDENLERİ
========================================================

## 1. alembic.ini — sqlalchemy.url değiştirildi

  Eskisi : sqlalchemy.url = driver://user:pass@localhost/dbname
  Yenisi : sqlalchemy.url = postgresql://rag_user:rag_password@localhost:5432/rag_db

  Alembic DB'ye bağlanmak için bu URL'i kullanır.
  localhost kullanıldı çünkü alembic komutu Windows
  terminalinden (Docker dışından) çalıştırılıyor.
  Docker container içinden çalışsaydı "db" yazılacaktı.

## 2. alembic/env.py — iki kritik ekleme yapıldı

  EKLEME 1 — Model import'ları:
    from app.db.base import Base
    from app.models import User

    Alembic modelleri görebilmek için bunları import etmek
    zorunda. Import edilmeden Base.metadata boş kalır,
    autogenerate hiçbir tablo üretemez.

  EKLEME 2 — target_metadata:
    Eskisi : target_metadata = None
    Yenisi : target_metadata = Base.metadata

    Base.metadata tüm model tanımlarını içerir. Alembic buna
    bakarak "DB'de ne olmalı?" sorusunu yanıtlar ve mevcut
    DB şemasıyla farkı bulur, migration'ı otomatik yazar.

========================================================
TEMEL ALEMBİC KOMUTLARI
========================================================

Migration oluştur (otomatik):
  alembic revision --autogenerate -m "create users table"
  → app/models içindeki modellere bakarak SQL üretir
  → alembic/versions/xxxx_create_users_table.py dosyası oluşur

Migration'ı uygula:
  alembic upgrade head
  → "head" = en son migration versiyonu
  → SQL PostgreSQL'e uygulanır, tablo fiziksel olarak oluşur
  → alembic_version tablosuna versiyon ID yazılır

Geri al:
  alembic downgrade -1   → bir adım geri
  alembic downgrade base → en başa dön

Mevcut durumu gör:
  alembic current        → DB hangi versiyonda?
  alembic history        → tüm migration geçmişi

========================================================
SECURITY.PY — ŞİFRE VE JWT TOKEN YÖNETİMİ
========================================================

## GENEL AMAÇ
Kullanıcı kimlik doğrulamasının iki temel parçasını yönetir:
  1. Şifre hash'leme ve doğrulama (bcrypt)
  2. JWT token üretme ve çözme (python-jose)

========================================================
KÜTÜPHANELER
========================================================

passlib + bcrypt:
  - Şifre hash'lemek için kullanılır
  - bcrypt kasıtlı olarak YAVAŞ çalışır → brute-force zorlaşır
  - MD5/SHA gibi hızlı algoritmalar şifre için tehlikelidir

python-jose:
  - JWT (JSON Web Token) üretmek ve doğrulamak için
  - JWT: kullanıcı kimliğini şifreli ve imzalı taşıyan string
  - Sunucu session tutmaz, token her istekte doğrulanır

========================================================
ŞİFRE YÖNETİMİ
========================================================

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")
  - bcrypt algoritmasını aktif eder
  - deprecated="auto": ileride algoritma değişirse eski
    hash'ler otomatik işaretlenir, sistem bozulmaz

verify_password(plain_password, hashed_password) → bool
  - Login sırasında kullanılır
  - Kullanıcının girdiği şifreyi DB'deki hash ile karşılaştırır
  - Plain text asla DB'de tutulmaz, karşılaştırma hash üzerinden

get_password_hash(password) → str
  - Kayıt sırasında kullanılır
  - Şifreyi bcrypt ile hash'ler
  - Her çağrıda farklı SALT üretilir → aynı şifre her seferinde
    farklı hash verir → rainbow table saldırısı engellenir

========================================================
JWT TOKEN ÜRETİMİ — create_access_token
========================================================

subject: str | int
  - Genellikle user.id — token kimin için üretildi

expires_delta: timedelta | None
  - Özel süre belirlenebilir, belirtilmezse config'deki
    ACCESS_TOKEN_EXPIRE_MINUTES (60 dk) kullanılır

datetime.now(timezone.utc)
  - Timezone-aware UTC zamanı kullanılır
  - Sunucunun lokal saatinden bağımsız
  - Farklı ülkelerdeki sunucularda tutarsızlık olmaz

JWT Payload (to_encode):
  "exp" → token'ın biteceği zaman (RFC 7519 standardı)
          kütüphane bunu otomatik kontrol eder
  "sub" → token sahibinin kimliği (user id string olarak)

jwt.encode(payload, JWT_SECRET_KEY, algorithm=JWT_ALGORITHM)
  - Payload secret key ile İMZALANIR
  - İmza olmadan herkes payload'ı değiştirebilir
    ("sub": "1" → "sub": "999" gibi yetki yükseltme)
  - Secret key ile imzalanınca sunucu değişikliği anlar

========================================================
JWT TOKEN ÇÖZME — decode_access_token
========================================================

Her korumalı API endpoint'inde çalışır.
jwt.decode() aynı anda 3 şeyi kontrol eder:
  1. İmza geçerli mi?     → secret key ile doğrular
  2. Süre dolmuş mu?      → "exp" claim otomatik kontrol edilir
  3. Algoritma doğru mu?  → farklı algoritmayı reddeder

Herhangi biri başarısız → JWTError → None döner → istek reddedilir
Başarılı → payload dict döner → payload["sub"] = user.id

========================================================
SALDIRI KORUMALARI
========================================================

DB sızıntısı        → bcrypt hash, plain şifre yok
Rainbow table       → her hash'e farklı salt
Token sahteciliği   → JWT imzası (secret key)
Süresi dolmuş token → "exp" claim otomatik kontrol
Algoritma karıştırma → algorithms=[...] ile kısıtlama
Brute-force         → bcrypt'in kasıtlı yavaşlığı

========================================================
KULLANıM AKIŞI
========================================================

KAYIT:
  kullanıcı şifre girer
      ↓
  get_password_hash() → bcrypt hash
      ↓
  hash DB'ye kaydedilir (plain şifre asla)

GİRİŞ:
  kullanıcı email + şifre gönderir
      ↓
  DB'den hash çekilir
      ↓
  verify_password() → eşleşirse True
      ↓
  create_access_token(user.id) → JWT token
      ↓
  token kullanıcıya gönderilir

KORUNAN ENDPOINT:
  istek → Authorization: Bearer <token>
      ↓
  decode_access_token() → payload veya None
      ↓
  payload["sub"] → user.id → DB'den kullanıcı çekilir
      ↓
  işlem yapılır veya 401 döner

SCHEMAS/USER.PY — API GİRİŞ/ÇIKIŞ ŞEMALARI
========================================================

## GENEL AMAÇ
models/user.py DB tablosunu tanımlar.
schemas/user.py API'nin ne alıp ne vereceğini tanımlar.
İkisi birbirinden kasıtlı olarak ayrıdır.

  models/user.py  → SQLAlchemy → DB katmanı → tüm kolonlar
  schemas/user.py → Pydantic   → HTTP katmanı → sadece API'ye açık alanlar

## UserCreate — Kayıt İsteği Şeması
POST /auth/register endpoint'ine gelen body bu şemaya göre
validate edilir.

  email: EmailStr
    → Sadece str değil, format kontrolü yapılır
    → "abc" veya "ali@" gelirse otomatik 422 döner

  password: str = Field(min_length=6, max_length=128)
    → min_length=6  : çok kısa şifre reddedilir
    → max_length=128: bcrypt'i DoS'lamak engellenir
    → Şifre buradan gelir ama DB'ye ASLA yazılmaz
    → security.py get_password_hash() ile hash'lenerek kaydedilir

  full_name: str | None = None
    → Opsiyonel, gönderilmezse None, kayıt yine kabul edilir

## UserRead — Kayıt Yanıtı Şeması
GET /users/me gibi endpoint'lerin response şeması.
API'nin kullanıcıya geri döndürdüğü veriyi temsil eder.

  Alanlar: id, email, full_name, is_active, is_superuser, created_at

  KRİTİK: hashed_password yok.
  DB'deki User modelinde bu alan var ama şemaya dahil edilmedi.
  API asla şifre hash'ini dışarı sızdırmaz. Bilinçli güvenlik kararı.

  model_config = {"from_attributes": True}
    → Pydantic v2 ayarı
    → Olmadan sadece dict'ten okuyabilir
    → Bu ayarla SQLAlchemy ORM nesnesinden doğrudan okur
    → db.query(User).first() → UserRead.model_validate(db_user) çalışır

## NEDEN AYRI SINIFLAR?
  İstek → UserCreate validate eder → iş mantığı
                                          ↓
                                  DB'den User nesnesi
                                          ↓
                          UserRead filtreler → response

  UserCreate : Gelen veriyi validate et, şifreyi kabul et
  UserRead   : Giden veriyi filtrele, hassas alanları gizle

========================================================
SCHEMAS/TOKEN.PY — JWT TOKEN ŞEMALARI
========================================================

## Token — Login Response Şeması
Login başarılı olunca API'nin döndürdüğü response.

  access_token: str
    → create_access_token() ile üretilen JWT string

  token_type: str = "bearer"
    → OAuth2 standardı, sabit "bearer" değeri
    → Client bunu alıp her istekte şu header'ı gönderir:
      Authorization: Bearer <token>

  Örnek response:
    {
      "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6...",
      "token_type": "bearer"
    }

## TokenPayload — JWT İçi Veri Şeması
Token decode edilince içinden çıkan payload'ı temsil eder.

  sub: str | None = None
    → security.py'da token üretilirken "sub": str(user.id)
      olarak set edilen user.id değeri
    → None olabilir: token geçersizse uygulama patlamaz

  Kullanım:
    payload = decode_access_token(token)
    token_data = TokenPayload(**payload)
    user_id = token_data.sub  # "42" gibi

## İKİ SINIFIN FARKI
  Token        → Login response'u dönerken  (API → Client)
  TokenPayload → Token doğrulanırken        (JWT içi → Uygulama)

========================================================
GENEL ŞEMA MİMARİSİ
========================================================

LOGIN AKIŞI:
  POST /auth/login (email + password)
      ↓
  UserCreate ile validate edilir
      ↓
  verify_password() → doğruysa
      ↓
  create_access_token(user.id)
      ↓
  Token şeması → {"access_token": "...", "token_type": "bearer"}

KORUNAN ENDPOINT AKIŞI:
  GET /users/me + Authorization: Bearer <token>
      ↓
  decode_access_token() → TokenPayload → sub = user.id
      ↓
  DB'den kullanıcı çekilir
      ↓
  UserRead şeması filtreler → response (şifre hash'i yok)

## NEDEN AYRI BİR SERVICE KATMANI?

  API endpoint  →  service       →  DB (model)
  (HTTP katmanı)   (iş mantığı)     (veri katmanı)

  Endpoint sadece HTTP işleriyle ilgilenir (istek al, response dön).
  İş mantığı service'te olur.
  Avantajlar:
    - Aynı mantık birden fazla endpoint'ten çağrılabilir
    - Test edilmesi kolaylaşır
    - Katmanlar birbirinden bağımsız değiştirilebilir

FONKSİYONLAR
========================================================

## get_user_by_email(db, email) → User | None
  db.query(User).filter(User.email == email).first()
  → SELECT * FROM users WHERE email = ? LIMIT 1
  → Kayıt yoksa None döner
  Kullanım: login + "email zaten kayıtlı mı?" kontrolü

## get_user_by_id(db, user_id) → User | None
  db.query(User).filter(User.id == user_id).first()
  → Token decode edilince sub alanından gelen user.id ile
    DB'den kullanıcı çekmek için kullanılır
  Kullanım: GET /users/me gibi korumalı endpoint'ler

## create_user(db, user_in: UserCreate) → User
  Adımlar sırasıyla:

  1. hashed_password = get_password_hash(user_in.password)
       → İlk iş: plain text şifre hemen hash'lenir
       → Bundan sonra plain şifre bir daha kullanılmaz

  2. user = User(email=..., hashed_password=..., ...)
       → ORM nesnesi oluşturulur
       → is_active=True  : yeni kullanıcı aktif başlar
       → is_superuser=False : sabit, güvenlik gereği
         (yeni kullanıcı asla admin olamaz)

  3. db.add(user)
       → Session'a eklenir, henüz DB'ye yazılmadı

  4. db.commit()
       → Transaction tamamlanır, INSERT SQL çalışır
       → Veri DB'ye fiziksel olarak yazılır

  5. db.refresh(user)
       → DB'nin atadığı id, created_at, updated_at
         değerleri Python nesnesine geri yüklenir
       → Bu olmadan user.id hala None olurdu

  6. return user
       → Endpoint bunu UserRead şemasına çevirir

## authenticate_user(db, email, password) → User | None
  Login işleminin tek fonksiyonu. Ya User döner ya None.

  user = get_user_by_email(db, email)
  if not user: return None
    → Email DB'de yok

  if not verify_password(password, user.hashed_password): return None
    → Şifre yanlış

  KRİTİK GÜVENLİK KARARI:
  "Email bulunamadı" ve "şifre yanlış" için AYRI mesaj verilmez.
  İkisi de None döner. Neden?
  → Saldırgan hangi email'in kayıtlı olduğunu anlayamasın
  → User Enumeration saldırısı engellenir

KATMANLARIN BİRLİKTE ÇALIŞMASI

POST /auth/register:
  UserCreate (validate) → create_user()
    ├── get_password_hash()        ← security.py
    ├── User(hashed_password=...)  ← models/user.py
    ├── db.add / commit / refresh  ← session.py
    └── User nesnesi döner
  UserRead (filtrele) → response

POST /auth/login:
  authenticate_user(db, email, password)
    ├── get_user_by_email()
    ├── verify_password()          ← security.py
    └── User veya None döner
  create_access_token(user.id)     ← security.py
  Token şeması → response

GET /users/me:
  decode_access_token(token) → sub = user.id
  get_user_by_id(db, user_id)
  UserRead (filtrele) → response

POST /auth/register
========================================================

@router.post("/register", response_model=UserRead, status_code=201)

  response_model=UserRead
    → Dönüş UserRead şemasından geçirilir
    → hashed_password otomatik çıkarılır, dışarı sızmaz

  status_code=201
    → Kaynak oluşturulunca standart HTTP kodu 201'dir (200 değil)

PARAMETRELER:
  user_in: UserCreate
    → Request body otomatik parse ve validate edilir
    → Geçersiz email veya kısa şifre → endpoint koda girmeden 422 döner

  db: Session = Depends(get_db)
    → get_db() generator çalışır, session enjekte edilir
    → İstek bitince otomatik kapatılır

AKIM:
  1. get_user_by_email() → email kayıtlı mı kontrol et
  2. Kayıtlıysa → 400 Bad Request + açıklayıcı mesaj
     (DB unique kısıtı da engeller ama bu daha önce çalışır,
      kullanıcıya anlamlı mesaj verir)
  3. create_user() → service katmanına devret
  4. Dönen User nesnesi → UserRead filtreler → response

POST /auth/login
========================================================

@router.post("/login", response_model=Token)
  → Response: {"access_token": "...", "token_type": "bearer"}

PARAMETRELER:
  form_data: OAuth2PasswordRequestForm = Depends()
    → FastAPI built-in OAuth2 form şeması
    → application/x-www-form-urlencoded formatı bekler (OAuth2 standardı)
    → Email gönderilse de alan adı "username"dir — standart böyle
    → form_data.username ve form_data.password ile erişilir

  db: Session = Depends(get_db)
    → DB session enjekte edilir

AKIM:
  1. authenticate_user() → email + şifre doğrula
     → None dönerse:
       401 Unauthorized + "Incorrect email or password."
       headers={"WWW-Authenticate": "Bearer"}
         → OAuth2 standardı zorunlu kılar
         → Tarayıcıya "bearer token bekliyorum" sinyali
       KRİTİK: "email mi yanlış şifre mi?" söylenmiyor
         → User Enumeration saldırısı engellenir

  2. is_active kontrolü
     → False ise 400 Bad Request + "Inactive user."
     → Soft-delete: hesap silinmez, devre dışı bırakılır
     → Devre dışı hesaba token üretilmez

  3. Token süresi config'den okunur (ACCESS_TOKEN_EXPIRE_MINUTES)
     create_access_token(subject=user.id, expires_delta=...)
     → user.id token'ın "sub" alanına yazılır

  4. Token(access_token=..., token_type="bearer") → response

get_current_user — KİMLİK DOĞRULAMA DEPENDENCY'Sİ
========================================================

Endpoint değil, dependency fonksiyonu.
Depends(get_current_user) yazılan her endpoint bu kodu çalıştırır.
Tekrar tekrar yazmak gerekmez.

PARAMETRELER:
  token: str = Depends(oauth2_scheme)
    → Authorization header'dan token otomatik alınır
  db: Session = Depends(get_db)
    → DB session enjekte edilir

KONTROL ADIMLARI (sırasıyla):

  1. decode_access_token(token)
     → None dönerse: 401 "Invalid authentication credentials."
     → Token geçersiz, süresi dolmuş veya imzası bozuk
     → Üç farklı hata aynı mesajla döner (hangisi olduğu söylenmez)

  2. payload.get("sub")
     → None dönerse: 401 "Invalid token payload."
     → .get() kullanılır — payload["sub"] KeyError fırlatır, güvensiz
     → Token geçerli ama içinde sub yoksa bozuk token

  3. get_user_by_id(db, int(user_id))
     → None dönerse: 401 "User not found."
     → Token geçerli ama kullanıcı silinmiş olabilir
     → Her istekte DB'den kontrol yapılır
     → Silinen kullanıcı token süresi dolana kadar erişemez

  4. is_active kontrolü
     → False ise: 400 "Inactive user."
     → Soft-delete: hesap silinmez, devre dışı bırakılır

  5. return user
     → Tüm kontroller geçildi, User ORM nesnesi döner

MODELS/ORGANIZATION.PY — ORGANİZASYON MODELLERİ
========================================================

## NEDEN BU DOSYA OLUŞTURULDU?
Platform multi-tenant: farklı şirketler (organizasyonlar) sistemi
kullanır. Her kullanıcının her organizasyonda farklı yetkisi olabilir.
Bu ilişkiyi üç ayrı yapıyla çözdük: OrganizationRole, Organization,
UserOrganizationRole.

## OrganizationRole(str, Enum)

class OrganizationRole(str, Enum):
    OWNER  = "owner"
    ADMIN  = "admin"
    MEMBER = "member"
    VIEWER = "viewer"

  str, Enum kombinasyonu neden?
  → str : DB'ye string olarak yazılır, JSON'a string olarak serialize
          edilir, karşılaştırma kolaylaşır ("owner" == OrganizationRole.OWNER)
  → Enum: geçersiz değer atanması önlenir, IDE autocomplete çalışır
  → plain str kullansaydık "ownr" gibi typo'lar runtime'a kadar fark
    edilmezdi

  Roller neden 4 tane?
  → OWNER  : organizasyonu kuran, siler, her şeye erişir
  → ADMIN  : üye ekler/çıkarır, ayarları değiştirir
  → MEMBER : doküman yükler, chat yapar
  → VIEWER : sadece okur, chat yapamaz
  İleride yetki kontrolü bu rollere göre yapılacak.

## Organization(Base)

__tablename__ = "organizations"

  id: Mapped[int] — primary_key=True, index=True
    → Her organizasyonun benzersiz kimliği
    → index → WHERE id=? sorguları hızlı

  name: Mapped[str] — String(255), nullable=False, index=True
    → Organizasyon adı zorunlu
    → index=True → isme göre arama yapılacak (admin panel, autocomplete)

  created_at / updated_at: DateTime, default=datetime.utcnow
    → Audit trail: ne zaman kuruldu, ne zaman değişti

  members = relationship("UserOrganizationRole",
                          back_populates="organization",
                          cascade="all, delete-orphan")
    → organization.members diyerek tüm üye kayıtlarına erişilir
    → cascade="all, delete-orphan": organizasyon silinince DB'de
      o organizasyona ait tüm UserOrganizationRole satırları da
      otomatik silinir, orphan (sahipsiz) kayıt kalmaz

## UserOrganizationRole(Base)

Kullanıcı ile Organizasyon arasındaki M:N (many-to-many) ilişkiyi
çözen junction (ara) tablo. Her satır "şu kullanıcı şu rolde şu
organizasyona üye" anlamına gelir.

__tablename__ = "user_organization_roles"

  __table_args__ = (UniqueConstraint("user_id", "organization_id",
                                      name="uq_user_organization"),)
    → Bir kullanıcı aynı organizasyona iki kez eklenemez.
    → DB seviyesinde kısıt — uygulama katmanı bypass edilse bile
      DB reddeder.

  user_id: ForeignKey("users.id", ondelete="CASCADE")
    → users tablosuna FK bağı
    → ondelete="CASCADE": kullanıcı silinince bu satırlar da silinir

  organization_id: ForeignKey("organizations.id", ondelete="CASCADE")
    → organizations tablosuna FK bağı
    → ondelete="CASCADE": organizasyon silinince bu satırlar da silinir

  role: Mapped[str] — String(50), default=OrganizationRole.MEMBER.value
    → Rolü string olarak saklar (enum.value: "member" gibi)
    → default=MEMBER: belirtilmezse üye olur, admin/owner elle verilmeli

  created_at: DateTime, default=datetime.utcnow
    → Ne zaman eklendi — raporlama ve audit için

  organization = relationship("Organization", back_populates="members")
    → user_role.organization diyerek Organization nesnesine ulaşılır
    → GET /organizations/me endpoint'inde nested response için kullanılır

  NOT: User modeline back_populates eklenmedi.
    → Fonksiyonel sorun yok ama ileride user_role.user erişimi
      gerekirse User modeline de relationship eklenmeli.

MODELS/USER.PY — GÜNCELLEME: organization_roles EKLENDI

## DocumentStatus(str, Enum)

class DocumentStatus(str, Enum):
    UPLOADED   = "uploaded"
    PROCESSING = "processing"
    COMPLETED  = "completed"
    FAILED     = "failed"

  str, Enum kombinasyonu neden?
    → str   : DB'ye ve JSON'a string olarak yazılır.
    → Enum  : Geçersiz durum ataması önlenir.
    → Durum geçişi:
        Yüklendi → Celery kuyruğa aldı → tamamlandı/hata
        UPLOADED → PROCESSING → COMPLETED veya FAILED
    → Celery worker'lar doküman işlerken bu durumu günceller.
      RAG pipeline'ın hangi aşamada olduğunu izlemek için.

## Document(Base) — Kolon Analizi

__tablename__ = "documents"

  id: Integer — primary_key=True, index=True
    → Her dokümanın benzersiz ID'si.

  organization_id: ForeignKey("organizations.id", ondelete="CASCADE")
    → Doküman hangi organizasyona ait.
    → ondelete="CASCADE": Organizasyon silinince o organizasyonun
      tüm dokümanları da otomatik silinir, orphan kayıt kalmaz.
    → index=True: "Bu organizasyonun dokümanlarını getir" sorgusu
      çok sık çalışacak, index kritik performans için.

  uploaded_by_user_id: ForeignKey("users.id", ondelete="SET NULL")
    → Dosyayı kim yükledi.
    → ondelete="SET NULL" (CASCADE değil): Kullanıcı silinse bile
      doküman korunur, sadece bu alan NULL olur.
    → nullable=True: Sistem/otomatik yükleme ihtimali bırakıldı.
    → Belge tarihçesi kullanıcı hesabından bağımsız tutulur.

  original_file_name: String(255), nullable=False
    → Kullanıcının yüklediği gerçek dosya adı (örn: "sözleşme.pdf").
    → Kullanıcıya gösterilir, indirme ekranında kullanılır.

  stored_file_name: String(255), nullable=False
    → Diskte saklanan UUID'li isim (örn: "a3f7...pdf").
    → original_file_name asla disk yolu olarak kullanılmaz.
    → Güvenlik: "../../../etc/passwd" gibi path traversal
      saldırıları önlenir. Kullanıcı girdisi disk'e yazmaz.
    → Aynı isimde iki dosya çakışmaz, her dosya benzersiz.

  file_path: String(500), nullable=False
    → Dosyanın diskteki tam yolu.
    → Celery worker dokümanı işlerken bu path'i kullanır.

  content_type: String(100), nullable=True
    → MIME tipi (application/pdf, application/vnd.openxmlformats...)
    → Dosya indirme endpoint'inde Content-Type header'ı için.

  file_size: Integer, nullable=True
    → Bayt cinsinden dosya büyüklüğü.
    → Kullanım kotası takibi için. (İleride: organizasyon
      başına maksimum depolama limiti)

  status: String(50), default=DocumentStatus.UPLOADED.value
    → RAG pipeline durumu. UPLOADED ile başlar.
    → index=True: "İşlenmemiş dosyaları getir" gibi sorgular için.

  created_at / updated_at: DateTime, default=datetime.utcnow
    → updated_at onupdate=datetime.utcnow: Durum her
      değiştiğinde (PROCESSING, COMPLETED...) otomatik güncellenir.

  organization = relationship("Organization")
  uploaded_by  = relationship("User")
    → ORM üzerinden ilişkili nesneye erişim.
    → back_populates eklenmedi: Henüz ters yönden erişim
      gerekmediği için tek yönlü bırakıldı.

## validate_file_extension(filename) → None | ValueError

ALLOWED_EXTENSIONS = {".pdf", ".docx", ".xlsx", ".xls", ".txt"}

  Path(filename).suffix.lower() kullanımı neden?
    → "RAPOR.PDF" → ".pdf" (büyük/küçük harf normalize edilir)
    → "dosya.tar.gz" → ".gz" (çift uzantılarda son kısım alınır)
    → Güvenlik: extension whitelist (izin verilenler listesi).
      Blacklist (yasaklılar listesi) yerine whitelist yaklaşımı
      daha güvenli: bilinmeyen her format otomatik reddedilir.
    → .exe, .sh, .py gibi tehlikeli dosyalar sunucuya alınmaz.

## save_upload_file(upload_file, stored_file_path) → int

  Chunk'lı okuma: 1 MB'lık parçalarda okur ve yazar.
    → Neden? 100 MB PDF doğrudan belleğe alınsaydı tüm dosya
      RAM'de tutulurdu. Büyük dosyalarda bellek patlaması.
    → 1 MB chunk: bellek sabit, dosya ne kadar büyük olursa olsun.
    → total_size sayacı: her chunk'ın boyutu toplanarak
      gerçek dosya boyutu hesaplanır (content-length header'ına
      güvenilmez, manipüle edilebilir).
  Return: int → bayt cinsinden toplam dosya boyutu.

## create_document_record(db, organization_id, uploaded_by_user_id,
                           upload_file) → Document

  Tüm adımlar sırasıyla:
  1. validate_file_extension() → izin verilen uzantı mı?
  2. create_upload_directory()  → klasör var mı, yoksa oluştur
  3. generate_stored_file_name()→ UUID'li güvenli isim üret
  4. os.path.join(upload_dir, stored_file_name) → tam yol
  5. save_upload_file() → dosyayı diske yaz, boyutu al
  6. Document(...) ORM nesnesi oluştur
  7. db.add / db.commit / db.refresh
  8. return document

  Önemli: Dosya önce diske yazılır, sonra DB'ye kaydedilir.
  Tersine yapılsaydı DB kaydı başarılı ama disk yazımı başarısız
  olabilirdi. Şu an DB başarılı ama disk başarısız olursa DB'de
  dosyasız kayıt kalır — bu bilinçli kabul edilmiş teknik borç,
  ileride transactional dosya yönetimi veya Celery ile çözülecek.

MODELS/DOCUMENT_CHUNK.PY — YENİ: CHUNK MODELİ
========================================================

DocumentChunk(Base) — "document_chunks" tablosunu tanımlar.
Her satır bir dokümanın metin parçasını temsil eder.

  id: Integer — primary_key=True, index=True
    → Her chunk'ın benzersiz ID'si.

  document_id: ForeignKey("documents.id", ondelete="CASCADE")
    → Hangi dokümana ait olduğu.
    → ondelete="CASCADE": Doküman silinince o dokümana ait tüm
      chunk'lar otomatik silinir.
    → index=True: "Bu dokümanın chunk'larını getir" sorgusu kritik,
      index olmadan N chunk için full table scan olur.

  organization_id: ForeignKey("organizations.id", ondelete="CASCADE")
    → Organizasyon bazlı erişim kontrolü için doğrudan tutulur.
    → Neden document üzerinden değil doğrudan burada?
      JOIN yazmadan "bu organizasyonun chunk'ları" filtrelenebilsin.
      İleride vector search sorguları bu alana göre filtre uygular.
    → ondelete="CASCADE": Organizasyon silinince chunk'lar da silinir.

  chunk_index: Integer, nullable=False, index=True
    → Chunk'ın belgedeki sırası (0, 1, 2...).
    → Sıralı listeleme ve context window oluşturma için gerekli.
    → index=True: ORDER BY chunk_index sorgularına hız sağlar.

  content: Text, nullable=False
    → Chunk'ın gerçek metin içeriği.
    → Text tipi seçildi çünkü String(N) için N belirsiz.
      Chunk boyutu 1200 karakter ama UTF-8 multibyte karakter
      ve overlap varken safe olmak için Text kullanıldı.

  page_number: Integer, nullable=True
    → PDF için sayfa numarası. PDF dışı dosyalarda NULL.
    → Kaynak gösterme (citation): "Bu bilgi sayfa 12'de."

  sheet_name: String(255), nullable=True
    → Excel için sayfa adı. Excel dışı dosyalarda NULL.
    → Kaynak gösterme: "Bu bilgi 'Bütçe 2024' sayfasında."

  source_type: String(50), nullable=True
    → Dosya türü: "pdf", "docx", "xlsx", "txt".
    → Farklı kaynak türlerini UI'da ayırt etmek için.
    → Neden nullable? Gelecekte başka kaynaklardan (URL, API)
      gelen chunk'lar için NULL bırakma esnekliği.

  created_at: DateTime, default=datetime.utcnow
    → Chunk ne zaman oluşturuldu.

  document = relationship("Document", back_populates="chunks")
    → chunk.document ile Document nesnesine ulaşılır.
    → back_populates="chunks": iki yönlü ilişki (document.chunks
      ve chunk.document birbirini bilir).

ParsedSection = dict[str, Any]
  → Her ayrıştırma sonucu: {"text": ..., "page_number": ...,
                             "sheet_name": ..., "source_type": ...}

## parse_txt(file_path) → list[ParsedSection]
  Tüm dosya tek bir section olarak döner.
  encoding="utf-8", errors="ignore": Bozuk karakterler atlanır,
  dosya yükleme başarısız olmaz.

## parse_pdf(file_path) → list[ParsedSection]
  PdfReader ile her sayfa ayrı section olur.
  page_number = sayfa numarası (1'den başlar).
  Boş sayfalar (text.strip() == "") atlanır.
  Neden sayfa bazlı?
    → PDF'in hangi sayfasından geldiği chunk'ta kaydedilir.
    → RAG sonuçlarında kaynak: "sayfa 5'te bu konudan bahsedilmekte."

## parse_docx(file_path) → list[ParsedSection]
  python-docx ile tüm paragraflar okunur, boşlar atlanır.
  Tek bir text string'e birleştirilir (join).
  Tüm dosya tek section → pdf gibi bölünmez çünkü docx'ta
  sayfa numarası güvenilir şekilde çıkarılamaz.
  page_number=None, sheet_name=None, source_type="docx"

## parse_xlsx(file_path) → list[ParsedSection]
  openpyxl ile her worksheet ayrı section olur.
  sheet.title → sheet_name alanına yazılır.
  Her satırın hücreleri " | " ile birleştirilir:
    ["Ahmet", "Satış", "150000"] → "Ahmet | Satış | 150000"
  Boş hücreler atlanır. Boş satırlar atlanır. Boş sheet atlanır.
  read_only=True: büyük Excel dosyalarında bellek tasarrufu.
  data_only=True: formül yerine hesaplanmış değer okunur.

## parse_document(file_path) → list[ParsedSection]
  Dispatch fonksiyonu. Extension'a göre doğru parser'ı çağırır.
  Bilinmeyen extension → ValueError fırlatır.
  Güvenlik: whitelist mantığı — sadece bilinen tipler işlenir.
  Yeni format eklemek: sadece buraya elif eklenir, başka kod değişmez.

SERVICES/CHUNKING_SERVICE.PY — YENİ: METİN BÖLÜCÜ
========================================================

## split_text_into_chunks(text, chunk_size=1200, chunk_overlap=200)
   → list[str]

  cleaned_text = " ".join(text.split())
    → Çoklu boşluklar, tab, newline tek boşluğa indirilir.
    → Tutarsız whitespace chunk sınırlarında tahmin edilemez
      davranışa yol açar. Normalize edilince chunk boyutları
      daha tutarlı olur.

  Sliding window algoritması:
    start = 0
    while start < text_length:
        end   = start + chunk_size       → chunk sonu
        chunk = cleaned_text[start:end]  → alınan parça
        start = end - chunk_overlap      → sonraki başlangıç

  chunk_overlap=200 neden?
    → Bir bilgi iki chunk arasına denk gelirse hiçbirinde
      tam olarak geçmez → LLM context'i anlayamaz.
    → 200 karakter overlap: her chunk'ın başı bir öncekinin
      sonuyla örtüşür. Bağlam kaybolmaz.
    → RAG kalitesi için kritik tasarım kararı.

## create_chunks_from_sections(sections, chunk_size=1200,
                                chunk_overlap=200)
   → list[dict[str, Any]]

  Her section için split_text_into_chunks çalışır.
  Global chunk_index korunur (section başında sıfırlanmaz).
  Her chunk dict'i:
    {"chunk_index": N, "content": "...",
     "page_number": ..., "sheet_name": ..., "source_type": ...}

  page_number ve sheet_name section'dan kopyalanır.
    → PDF'in 3. sayfasından gelen tüm chunk'lar page_number=3 taşır.
    → Excel'in "Bütçe" sheet'inden gelen chunk'lar sheet_name="Bütçe".

SERVICES/DOCUMENT_PROCESSING_SERVICE.PY — YENİ: İŞLEM ORKESTRATÖRü
========================================================

process_document(db, document_id) → Document

Bu fonksiyon tüm pipeline'ı yönetir:
parse → chunk → DB'ye yaz → status güncelle

## Akış Detayı:

1. document = db.query(Document).filter(id == document_id).first()
   → Doküman yoksa ValueError fırlatılır (API 400'e çevirir).

2. document.status = PROCESSING → db.commit()
   → İşlem başladı sinyali. Uzun süren dosyalarda UI bu durumu gösterir.
   → Neden hemen commit? İşlem çökse bile PROCESSING durumu kalır,
     monitör/admin "takılı kalan" işlemleri görebilir.

3. sections = parse_document(file_path)
   → Parser service dosyayı okur, section listesi döner.

4. chunks = create_chunks_from_sections(sections)
   → Chunking service section'ları chunk'lara böler.

5. Mevcut chunk'ları sil:
   existing_chunks = db.query(DocumentChunk).filter(document_id).all()
   for chunk in existing_chunks: db.delete(chunk)
   db.flush()
   → Neden? Doküman yeniden işlenirse (reprocess) eski chunk'lar
     temizlenir, çift kayıt oluşmaz.
   → db.flush(): silmeler SQL'e çevrilir ama commit edilmez.
     Yeni chunk'lar eklenmeden önce çakışma riski ortadan kalkar.

6. Yeni chunk'ları ekle:
   for chunk in chunks:
       document_chunk = DocumentChunk(document_id, organization_id,
                                       chunk_index, content, ...)
       db.add(document_chunk)

7. document.status = COMPLETED → db.commit() → db.refresh()
   → Tüm chunk'lar ve durum tek commit ile yazılır (atomik).

## Hata Yönetimi (except Exception):

   db.rollback()
   → Yarım yazılan chunk'lar geri alınır.

   document yeniden sorgulanır:
   → Rollback sonrası eski nesne geçersiz (detached state).
     Yeni sorgu ile taze nesne alınır.

   document.status = FAILED → db.commit()
   → Hata durumu DB'ye yazılır.

   raise
   → Hata üst katmana iletilir, API 500 veya 400 döner.

  Neden rollback sonrası yeni sorgu?
    → db.rollback() sonrası session'daki ORM nesneleri
      "detached" olur. Onlar üzerinden işlem yapılmaya
      çalışılırsa "Instance is not bound to a Session" hatası alınır.
      Yeni db.query() ile taze nesne almak zorunlu.
